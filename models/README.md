# RideMatch Models and Metrics

This document explains what RideMatch scores, what each metric means, how the
metrics interact, and where to inspect the reasoning behind a decision.

## What Runs Where

RideMatch has three decision paths:

| Path | Input | Output | Purpose |
| --- | --- | --- | --- |
| Nearest-driver baseline | Driver distance | Nearest available driver | Simple operational benchmark |
| Classifier GBDT | 12 online features | Probability of `matched` | Imitates the simulator's nearest-driver label |
| Utility GBDT | 12 online features | Candidate utility score | Ranks candidates using delay, acceptance, cancellation, and supply signals |

The API and Docker Compose serving default is `utility_model.pkl`. Set
`RIDEMATCH_MODEL_PATH=/app/models/model.pkl` to serve the classifier artifact.
If no artifact is available, the API uses a nearest-driver heuristic and returns
`heuristic_fallback`.

The two model artifacts are not directly comparable by raw score:

- Classifier scores are probabilities from `0` to `1`. Higher means the model
  predicts a higher chance that the candidate matches the simulator label.
- Utility scores are regression outputs. They are not probabilities or dollars.
  They can be negative. Only their ordering within the same request matters;
  the highest score wins.
- The baseline has no learned score. It selects the smallest pickup distance.

## Online Feature Contract

Both GBDT models consume the same 12 columns, in this order:

1. `distance_km`: straight-line driver-to-pickup distance. Lower generally helps.
2. `eta_minutes`: simulated ETA, equal to distance times `2.5`. Lower helps.
3. `driver_idle_minutes`: time since the driver became available. The utility
   target gives some credit to longer idle time.
4. `available_drivers`: current supply. This changes market pressure and the
   model's context; it is not a quality score by itself.
5. `open_requests`: current demand. More open requests increase pressure.
6. `demand_supply_ratio`: `open_requests / max(1, available_drivers)`. Higher
   means a tighter marketplace.
7. `hour_of_day`: local simulation hour.
8. `is_peak`: rush-hour flag for 07:00-09:00 and 17:00-19:00.
9. `driver_acceptance_rate`: historical acceptance observed before this attempt.
10. `same_pickup_zone`: whether the driver is in the requester's 5 km zone.
11. `pickup_zone_supply`: available drivers in that local zone.
12. `pickup_zone_demand_supply_ratio`: local demand divided by local supply.

The feature builder derives `demand_supply_ratio` and `is_peak`. Delayed fields
such as `realized_wait_minutes`, `cancelled`, and the utility target itself are
not online inputs.

## Candidate Scores

A candidate score answers: "How attractive is this driver for this request?"
The API computes a score for every supplied driver and selects the maximum.
The UI exposes the selected score, all candidate scores, distance, ETA,
historical acceptance, and local availability in the driver table.

The utility target is generated by the simulator as a transparent experiment:

```text
utility =
    - eta_minutes
    - 0.25 * ride_minutes
    + 0.05 * driver_idle_minutes
    - 12.0 * pickup_cancellation_risk
    + 2.0 * driver_acceptance_probability
    + 3.0 * historical_acceptance_rate
    - 12.0 * rider_cancellation_probability
    - 0.5 * demand_pressure
    - 1.0 * peak_friction
    + 1.5 * same_pickup_zone
    - 0.25 * local_demand_supply_ratio
```

This is a synthetic target, not a claim about a production rideshare objective.
It intentionally makes the tradeoffs inspectable. For example:

- A nearer driver usually improves ETA, ride time, and cancellation risk.
- A driver with stronger historical acceptance can outrank a slightly nearer
  driver when the acceptance benefit offsets the distance penalty.
- A long-idle driver receives a modest fairness/reliability benefit.
- Peak friction and high local demand pressure reduce utility.
- Same-zone drivers receive a local proximity bonus.

The trained utility GBDT learns an approximation of this target from historical
candidate rows. It may not reproduce the exact terms because it sees finite,
noisy data and is evaluated on a later time slice.

## Operational Metrics

Candidate metrics describe ranking or prediction. Operational metrics describe
what happens after one driver is selected for each request. Policy replay runs
the nearest-driver and learned policies on the same seeded request stream so
these metrics can be compared fairly.

| Metric | Definition | Higher/lower is better | Interaction with other metrics |
| --- | --- | --- | --- |
| Coverage | Matched requests / all requests | Higher | A policy can raise coverage while worsening wait or cancellations |
| Average wait | Mean simulated wait across all requests | Lower | Useful overall summary, but can hide a bad long tail |
| P90 wait | 90th-percentile simulated wait | Lower | Exposes tail pain that average wait can conceal |
| SLA hit rate | Requests with wait at or below 5 minutes / all requests | Higher | Closely related to P90, but tied to a fixed service promise |
| Driver rejection rate | Selected assignments rejected by drivers / all requests | Lower | A model can improve distance while selecting less willing drivers |
| Rider cancellation rate | Requests cancelled by riders / all requests | Lower | Usually rises with long waits, demand pressure, and peak friction |
| Cancellation rate | Any cancelled assignment / all requests | Lower | Includes driver rejection and rider cancellation effects |
| Utilization | Matched ride minutes / (`drivers * simulation steps`) | Higher, within capacity | More utilization is useful only if coverage and wait remain acceptable |
| Policy KPI score | Weighted change versus nearest baseline | Higher than zero | A summary for model selection, not a probability or business dollar value |

The current policy KPI score is:

```text
2.0 * (baseline average wait - model average wait)
+ 1.5 * (model coverage - baseline coverage)
+ 1.0 * (model SLA rate - baseline SLA rate)
+ 1.0 * (baseline cancellation rate - model cancellation rate)
+ 0.5 * (model utilization - baseline utilization)
```

A positive score means the learned policy's weighted outcome changes are better
than nearest-driver under this replay. A negative score means the baseline wins
under these weights. The weights are experiment choices; they do not establish
that one minute, one percentage point of coverage, and one utilization unit
have equal business value. Inspect the component deltas before trusting the
composite score.

## Prediction Metrics Versus Policy Metrics

These metrics answer different questions:

- ROC AUC asks whether the classifier orders positive and negative candidate
  rows correctly across thresholds. It does not prove better request-level
  fulfillment.
- Precision asks how often classifier-positive candidate rows are actually
  labeled positive. Recall asks how many positive rows it finds. Both depend on
  the simulator's nearest-driver label and are not direct rider outcomes.
- Utility validation MAE asks how close predicted utility is to the synthetic
  utility target on the held-out time slice. Lower is better, but lower MAE does
  not guarantee better coverage, wait, or cancellation outcomes.
- Ranking accuracy asks how often the top model-scored candidate equals the
  generated `matched` candidate. It is a candidate-table diagnostic.
- Policy replay KPIs are the primary decision evidence because they simulate the
  consequences of selecting one driver per request.

Do not compare a classifier probability, a utility score, a fare, and a policy
KPI as though they share a scale. They serve different stages of the system.

## Fare Is Separate From Matching

The fare estimate is not the utility score and does not decide which driver is
selected. It is a transparent pre-ride estimate:

```text
base = 3.00 + 1.45 * distance_km + 0.18 * eta_minutes
pressure = open_requests / max(1, available_drivers)
surge = min(2.5, 1.0 + 0.25 * pressure)
estimated_fare = base * surge
```

More nearby riders increase pressure. More available drivers reduce pressure.
The multiplier is capped at `2.5x`. The API and UI show the fare and surge for
each candidate. Post-ride billing is not implemented: there is no dropoff-based
route or actual trip-meter calculation in the current API.

## Explainability Surfaces

The project exposes reasoning at several levels:

1. The API response includes every candidate's distance, ETA, fare, surge, and
   model score, plus the selected driver's score.
2. The web console shows the selected candidate, a "Why this match?" panel,
   historical acceptance, local driver count, and the full candidate table.
3. `src/models/feature_importance.py` computes held-out permutation importance.
   It uses ROC AUC for the classifier and negative MAE for the utility model.
   A positive importance means shuffling that feature worsened the chosen
   validation metric; importance is not causal evidence.
4. `src/models/policy_eval.py` reports outcome-level deltas against the same
   nearest-driver request stream.

Run the explainability and policy checks after training:

```bash
python -m src.models.feature_importance \
  --model models/utility_model.pkl \
  --input data/processed/synthetic_matches.csv

python -m src.models.policy_eval \
  --model models/utility_model.pkl \
  --drivers 40 --riders 600 --steps 1440 --seed 42
```

## Known Limitations

- The simulator is synthetic and does not represent Lyft's internal data.
- The classifier label comes from nearest-driver behavior, so it mostly tests
  imitation rather than independent treatment-effect improvement.
- The utility target is hand-specified and delayed; it is an experiment.
- Straight-line grid distance stands in for road routing.
- The current `ride_minutes` approximation is derived from pickup distance.
- Post-ride billing, tolls, wait-time charges, and actual dropoff routes are not
  modeled.
- Permutation importance is a sensitivity diagnostic, not causality.
- The policy KPI score is a weighted research metric and should be reviewed with
  every component metric before a policy decision.

## Reproduce the Artifacts

```bash
python src/simulator/generate_data.py \
  --drivers 40 --riders 600 --steps 1440 \
  --output data/processed/synthetic_matches.csv
python src/models/train_model.py \
  --input data/processed/synthetic_matches.csv \
  --output models/model.pkl
python src/models/train_utility_model.py \
  --input data/processed/synthetic_matches.csv \
  --output models/utility_model.pkl
```

Model binaries and generated CSVs are ignored by Git. This README remains
tracked in `models/` so the artifact contract and evaluation assumptions travel
with the code.
